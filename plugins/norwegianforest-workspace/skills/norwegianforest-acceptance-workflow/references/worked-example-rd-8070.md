# 實例：RD-8070 大哥付分期付款交易建立函式（Reserve）

本文件記錄一次實際的驗收，用來說明流程中每一步實際會遇到什麼。卡片內容與 PR 是當時的狀態，僅作為案例。

## 背景

- 卡片：RD-8070「[NorCat] 大哥付分期付款交易建立函式（Reserve）」，PR #25986（open），異動橫跨 NorwegianForest 與 Van
- 設計：兩階段。`建立大哥付分期付款交易` 只建立 PENDING 骨架；`確認大哥付分期付款交易` 經 Van 呼叫大哥付 Reserve，成功後更新為 UNPAID
- 起因：使用者呼叫 confirm 得到「大哥付建立交易失敗（904）：缺少items」

## 過程與學到的事

**1. 由錯誤訊息回程式碼找出處（Step 3）**
錯誤訊息的格式與 `callVanReserve` 拼出的訊息一致，確認是 Reserve 請求出的錯。讀請求 body 發現沒有 `items`；讀 Van 的轉發程式發現它只補通知網址、加密個資，其餘原樣轉發，所以整條路徑都沒人帶 `items`。再查廠商規格書：`items` 被列為非必要，實測卻是必要。**規格書與實測不一致時，以實測為準，並把落差寫進報告。**

**2. 先寫會失敗的測試，再修正**
在既有的「成功送出」測試補上對 `items` 的斷言，確認它因缺 `items` 而失敗，修正後轉綠。全新 worktree 的三個坑都踩到了：沒有 `node_modules`、缺 `JavaCat/worker.js`、缺 NorwegianForest 建置產物。**建置產物缺失時全部測試都紅，看起來像大範圍壞掉，其實是假紅燈**（錯誤是「腳本應預設匯出函數」）。

**3. dev 要先 patch（Step 4）**
使用者自己在 dev 執行 patch。之後第一次呼叫得到「找不到函數」：函式是以中文名稱註冊的，我用了腳本檔名。

**4. `argument` 雙重序列化**
改用中文名稱後得到「缺少銷售單編號」，實際上參數有傳。原因是 client 的 `call` 會自己 `JSON.stringify`，我照 skill 文件先手動轉了一次。此後腳本內建防呆。

**5. 外部測試站只認特定測試對象（Step 5）**
使用者提供的兩支門號都回 017（非大哥大用戶）。這代表請求已通過欄位檢查（之前是 904），但號碼不被測試站接受。**這裡繞了遠路：應該先讀廠商的測試參數文件。** 文件寫明測試站只認廠商提供的 5 組測試門號，且呼叫前要通知廠商。改用其中一支後 confirm 成功，紀錄由 PENDING 更新為 UNPAID，交易編號、付款連結、QR 碼都回填。

**6. 冪等性驗證**
對同一筆已成功的紀錄再呼叫一次 confirm，回傳同一組交易編號與連結、沒有錯誤，代表走了冪等短路，沒有再打廠商。同單號連建兩筆互不覆蓋的條件，則在 dev 上找到既有的兩筆獨立紀錄佐證。

**7. 判定時的發現（Step 6）**
初版報告用了「部分通過」，依現在的規則應改成拆子項：

| 原條件 | 拆分後 |
|---|---|
| 3：非大哥大門號立即報錯、紀錄保留，且「不會呼叫到 Reserve」 | 3a 立即報錯且紀錄仍為 PENDING ✅；括號註記列入「條件與現況的落差」——實際上 017 正是 Reserve 回的，因為專案在 9/23 決定不做前置門號驗證 |
| 4：通知廠商失敗時紀錄保留 | 4a 業務失敗（017）紀錄保留 ✅；4b 連線中斷／逾時 ⚠️ 僅單元測試涵蓋 |

同時發現 **PR 描述寫「先經 Van 驗證門號，通過後才呼叫 Reserve」，程式碼沒有這一步**，列為落差。

**8. 收尾（Step 8）**
- dev 留下 3 筆測試紀錄，列給使用者決定，未清理。
- worktree 借了主 checkout 的 `node_modules`（符號連結），先 `rm` 三個連結再移除 worktree。
- 修正的 commit 尚未推送，只存在本機分支上，所以不用 `ExitWorktree(remove)`，改用 `keep` 離開再手動移除，保留分支。

## 這次做得不夠好、流程已改進的地方

- 一開始把「實測」丟回給使用者，沒有先確認 MCP 能做什麼。現在 Step 0 明列 MCP 沒有 function 呼叫工具，並提供腳本。
- 打外部測試站之前沒有先查廠商文件，白打了兩次。現在 Step 2 要求列完清單就一次問清測試對象與限制。
- 初版判定用了「部分通過」。現在改為拆子項。
