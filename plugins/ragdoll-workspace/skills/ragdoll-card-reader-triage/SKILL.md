# Ragdoll 刷卡機（台新 ECR）門市回報診斷 SOP

## 目標與適用範圍

**輸入**：門市的問題回報包（`production_issue-<日期>-<門市>-<機台>/`）。強烈建議再向維運索取代理程式 log
（`C:\ProgramData\POSAgentDotNet\logs`，含 `posagentdotnet-*.log` 與 `printer-serialdata-*.log`），可大幅提高結論信心。

**輸出**：① 初判「程式 vs 硬體線路」與信心等級 ② 證據（已證明／推論／未知）③ 調查報告 ④ 給維運的白話文案。

**適用**：`CREDIT_CARD_READER_TYPE = TSB_ECR`（台新 400B，經 ECR.exe）。
**不適用**：新光（SKB）、玉山（ESUN）等其他刷卡機——它們的通訊協定不同，`triage.py` 的 ECR 章節不適用；
只能套用本 SOP 的通用部分（Step 3 排除程式變更、Step 4 中台對照組、Step 5 帳務）與 `references/decision-tree.md` 的分層思路。

## 核心思路（為什麼這樣能分辨程式與線路）

刷卡是一條鏈，每一層都留下不同的證據。**找出「第一個壞掉的層」，結論就出來了。**

```
Ragdoll ─HTTP─▶ POSAgentDotNet 代理程式 ─in.dat─▶ ECR.exe ─COM1 115200 8N1─▶ 刷卡機 ─▶ 銀行
```

判斷靠三條軸，缺一條信心就要降：

1. **時間軸**：發病點前後有沒有變更（版本、代理程式更新／重啟、種子名單生效、設定）。沒有變更吻合 → 不像 regression。
2. **對照軸**：同店他機、他店同期的正常刷卡比例。他機正常 → 不像全店或共通的程式缺陷。
3. **層級軸**：失敗的**型態**落在哪一層（無回應、亂碼、多餘垃圾、ACK 後損壞、核准卻顯示失敗）。

> **「沒有變更」不等於「沒有 bug」。** 證據只支持「沒有 regression、沒有處理錯誤」時，結論寫「未發現證據」，
> 不寫「排除」。潛伏缺陷可能在新的環境條件下才被觸發，所以要逐項檢驗（殭屍程序、COM1 搶用、overrun、速率不符），
> **資料能查的先查完，再說「需要現場」**。

## Step 0：確認輸入與資料安全

1. 回報包要先解壓到**專屬的新資料夾**（下載檔視為不可信資料）。**檔案導覽**：

   | 檔案 | 用途 |
   |---|---|
   | `description.txt` | **門市原話**：報告的「門市描述」直接引用，不要改寫 |
   | `metadata.json`、`ragdoll-store.json` | 門市、機台、**回報當下**的版本、`POS_CONFIG_NAME`、`CREDIT_CARD_READER_TYPE` |
   | `ecr/log/`、`ecr/transmitted/` | ECR.exe 的 log 與 in／out.dat 歸檔（`triage.py` 的主要輸入） |
   | `offline-mutable.snapshot.db` | 本機交易（只含這台機台）：正常刷卡 vs 手 KEY、調閱編號 |
   | `offline-readonly.snapshot.db` | 同步下來的唯讀資料，含種子名單 `pos_pilot*` |
   | `screenshot.png` | 門市按下回報當下的畫面（常能看出是哪張單、付款方式） |
   | `logs/credit-card`、`logs/main` | Ragdoll 端的開機偵測與啟動事件；**通常只保留最近約 3 天** |
   | `logs/auto-update` | Ragdoll 版本切換時間（同樣只有近幾天） |
   | `config.ini` | Ragdoll 自己的設定，**不是** ECR 的設定檔 |
   | `storeSnapshot.json` | Ragdoll 前端狀態快照，刷卡診斷通常用不到 |

   缺 `ecr/` 就請門市重送（問題回報按鈕）；機台若不走 ECR（非 TSB_ECR）見上方「不適用」。
2. 讀 `metadata.json`（門市、機台、`posVersion`、回報時間）與 `ragdoll-store.json`。
   注意 `posVersion` 是**回報當下**的版本，不是發病當時的版本。
   `logs/credit-card` 每天開機會有一行 `detectTsbSubtype: 3 秒無回應，判定為 TSB_ECR（400-byte 裝置）`，**這是正常的**
   （400B 刷卡機本來就不回應 144B 探測封包），不是異常訊號。
3. **唯讀、不印卡號。** 用 `python3 -I` 執行腳本、路徑以參數傳入、不要 `cd` 進下載資料夾；SQLite 只以唯讀開啟；
   `out.dat`、`reconcile_info` 只統計格式，不輸出內容。
4. 要查中台時只做唯讀查詢；**不寫入、不建 Jira、不留言、不 commit**，除非使用者明確要求。

## Step 1：跑分析腳本

```bash
python3 -I <本 skill 目錄>/scripts/triage.py <回報包目錄> [--agent-logs <代理程式 log 目錄>]
python3 -I <本 skill 目錄>/scripts/triage.py --selftest      # 修改腳本後必跑；12 個判定、穩健性與帳務比對情境
```

腳本只用標準庫（Python 3.9+）。輸出 Markdown；`--json` 輸出摘要；`--onset YYYY-MM-DD`（或精確到 `YYYY-MM-DD HH:MM`）可覆蓋自動偵測的發病點。

`--no-sw-change`、`--control-ok` 是**使用者宣告**（Step 3、Step 4 做完才帶），腳本無法驗證；
輸出會在依據中標示「使用者宣告」，報告必須附上你實際查到的證據。沒有 `--agent-logs` 時，信心最高只到「中高」。

| 輸出章節 | 看什麼 |
|---|---|
| 初判 | 標籤（硬體／線路、程式疑點、刷卡機端、無問題、無法判定）、**三列信心表**、依據、待確認項 |
| 1. ECR 通訊紀錄 | 發病日、逐日失敗率、失敗型態、**損壞封包鑑識**；1.4：區塊完整性（殭屍）、請求樣板前後是否一致、NAK 次數、**重試重複扣款風險** |
| 2. 歸檔 out.dat | 空白範本（`TEMPLATE:0001`／`0003`）vs 刷卡機自己回報的結果（`TERMINAL_REPLY`，帶細項碼） |
| 3. 帳務對帳 | 手 KEY 規模、**調閱編號缺口 vs 手 KEY 筆數**、每筆手 KEY 的失敗前因、核准後仍手 KEY（金額相同且未入帳）、預估刷卡機目前編號、未遮罩卡號統計 |
| 4. 種子名單 | 這台走 POSAgentDotNet 還是 Ragdoll 直連、名單生效日 |
| 5. 代理程式 log | 版本時間軸、啟停事件、in／out 成對、發病後新訊息類型、out.dat 逐日解碼 |
| 6. COM3 探針 | PC 整體序列系統是否健康（發票機每 30 秒探針的回應延遲與缺失） |

## Step 2：讀懂失敗型態

| 型態（腳本輸出） | 意思 | 指向 |
|---|---|---|
| `APPROVED` | 完整結果框、`0000` | 正常 |
| `TERMINAL_REPLY` | 完整結果框但回應碼非 `0000`（常帶細項碼：02XX 授權失敗、03XX 逾時、04XX 取消） | **刷卡機端**（客戶、銀行、操作），不是線路 |
| `SILENT` | 完全沒收到任何位元組（ECR `[16]`／`[14]`） | 線路，但分不出請求沒到或回覆沒回 |
| `ACK_THEN_BAD` | 收到 `0606` 但結果損壞（ECR `[17]`） | **請求有送達、回程損壞**（最強的線路證據） |
| `GARBLED_NO_ACK` | 沒 ACK、卻收到一串無法解析的亂碼 | 線路雜訊或速率不符（看乾淨框有無交錯） |
| `NOISE_ONLY` | 只收到 1～16 bytes 雜訊 | 接收線上有雜訊 |

損壞型態的讀法（多於 403 bytes＝雜訊型；乾淨框夾在損壞之間＝非靜態設定不符；全亂碼無乾淨框＝速率不符；
只有縮短的框＝overrun）詳見 `references/decision-tree.md` §3。

## Step 3：人工排除程式變更（MUST）

腳本看不到 git，這步要人工做。目的：確認發病點前後**沒有**任何 Ragdoll／代理程式的變更。

```bash
# 發病日 vs Ragdoll 版本 tag（tag 日期晚於發病日 → 那一版不可能是原因）
git -C <petpetgo> for-each-ref --format='%(refname:short) %(creatordate:format:%Y-%m-%d %H:%M)' 'refs/tags/ragdoll-v*'
# 信用卡機模組有沒有動：
#   發病當時的版本已知 → 取「發病前最後一版」..「回報版本」
#   版本不明（posVersion 是回報當下版本，auto-update log 只有近幾天）→ 取「發病前約 30 天的 tag」..「回報版本」整段
git -C <petpetgo> log --format='%h %ad %s' --date=short <起點tag>..<回報版本tag> -- Ragdoll/electron/main/devices/credit-card
# 代理程式 repo 在發病前後有沒有 commit
git -C <petpetgo> log --since=<發病日-14天> --format='%h %ad %s' --date=short -- OldEnglish
```

再檢查（腳本已輸出：代理程式版本與啟停事件、種子名單生效日、請求封包樣板、區塊完整性）：種子名單生效日是否與**首次失敗日**相差 3 天內、
`ECR.exe` 檔案時間、`logs/auto-update`（Ragdoll 版本切換時間，只有近幾天）。
請求封包每筆的調閱編號、金額、日期時間、機台時戳本來就不同，所以腳本是**遮蔽這些欄位後比樣板**，不是逐字比對。

**發病當時的 Ragdoll 版本若無法證實**（常見：log 已輪替），報告就寫「發病當時版本無法證實」，
以「信用卡機模組在整段版本範圍零變動」＋「請求樣板前後一致」＋「代理程式未變」作為替代證據，信心不要寫「高」。

> `CS_ecr.dat` 是 ECR 的設定檔，但**每次交易都會被改寫，修改時間不能判斷設定有沒有變**；根目錄 `config.ini` 是 Ragdoll 自己的設定，與 ECR 無關。

全部確認「無變更吻合」→ 之後重跑加 `--no-sw-change`。任何一項吻合 → 優先懷疑該變更，初判改為程式疑點。

## Step 4：人工查中台對照組（MUST）

查同店他機、他店同期的「正常刷卡 vs 手 KEY」比例，細節與 filter 範例見 `references/middleplatform-queries.md`。
重點：`summarize` 帶表身條件要**單發依序**執行；美容單在 `posservicesale`；要逐機台算比例、同時查發病前基準。

- 他機正常、只有這台崩潰 → 單機問題。
- 多機同時從同一時間壞 → 偏共同原因（版本、更新、環境），**不要**用本 SOP 的「線路」文案。
- PM／門市說「多間店都有」時，逐機台回覆比例，並說明個位數的手 KEY 屬背景雜訊。
- **發病前基準窗口**取「發病前 9～14 天」（與發病後天數相近），發病後取到查詢當下，報告註明查詢時間。
- 美容單的付款表身在 `posservicesale` 也叫 `payments`，條件寫法相同。
- **他機的 Ragdoll／代理程式／ECR 版本查不到**（中台與回報包都沒有）。報告寫「同在種子名單，版本未查證」，不要寫「同版本」。

確認「同店對照機台同期正常」→ 重跑加 `--control-ok`。

## Step 5：帳務與風險

- **調閱編號對帳**（腳本已算）：成功交易之間的編號缺口＝刷卡機有交易但 POS 沒記到；缺口 = 期間手 KEY 筆數，表示每筆手 KEY 都對應一次刷卡機交易。
  發病前的小缺口多半是取消或被拒絕的交易佔用編號，屬正常。
- **手 KEY 的前因**（腳本已算）：每筆手 KEY 前 10 分鐘內有沒有「金額相符的失敗 ECR 呼叫」。找不到的可能是指定金額分次付款或沒先刷就手 KEY，
  列出來由使用者判斷，不要自行當成異常。
- **核准後仍手 KEY** 只有在「金額相同、5 分鐘內、且該核准沒有對應的入帳」時才算疑點；只看時間會把「另一筆」誤報（曾發生）。
- **重試風險**（腳本 1.4 表）：刷卡機已收下請求（ACK）但結果損壞，隨後同金額重試核准——調閱編號連號＝失敗那次沒佔用編號；
  出現缺口＝需對結帳單。另外**請問店員**：POS 顯示失敗後，是在 POS 再刷一次，還是直接在刷卡機上單機再刷一次（後者才會多出沒有 POS 紀錄的交易）。
- **措辭**：寫「刷卡機端皆有對應交易編號，是否扣款需以刷卡機結帳單核實」，**不要寫「都已扣款」**。
  最後一筆成功之後無法再對帳，重複扣款只能靠結帳單確認；腳本給預估的刷卡機目前編號，差距大代表可能有重刷或漏記。
- **附帶風險**：手 KEY 離線刷卡的卡號欄位（`reconcile_info`）若有未遮罩的純數字，是資安議題，與故障原因無關，
  **只描述事實與影響、不自行建票**，由使用者決定。

## Step 6：判定與信心

照 `references/decision-tree.md` 的規則（腳本已實作，人工判讀時對照）。結論一定分三類寫：

- **已證明**：附證據（時間點、次數、檔案）。
- **推論**：附推論依據與驗證路徑。
- **未知**：附如何查。

信心上限：沒完成 Step 3、Step 4 且沒有代理程式 log，最高只能「中高」；三者都到位才能寫「高」。
即使「高」，也**只代表故障層在序列通訊層**；具體是線材、接頭、轉接頭、COM1 埠硬體還是刷卡機該埠，資料無法區分，
必須現場對調測試（`decision-tree.md` §5）。

若初判不是「硬體／線路」（核准卻顯示失敗、有程式疑點、刷卡機端、無問題、無法判定），**不要用線路的維運文案**，
改依 `decision-tree.md` §6 說明該往哪裡查。

## 需要另外向門市或維運索取的資料（回報包本來就沒有）

| 資料 | 向誰要 | 為什麼 |
|---|---|---|
| 刷卡機結帳單（發病日起） | 門市 | 核對是否扣款、有無重複扣款；調閱編號區間 |
| 代理程式 log 整個資料夾（含 `printer-serialdata-*.log`） | 維運 | 代理程式是否正常、COM3 探針；沒有它信心最高只到「中高」 |
| 收銀機 Windows 事件檢視器（系統事件，序列埠與 USB 轉接器相關） | 維運 | 排除發病夜間的更新或驅動事件 |
| 裝置管理員中 COM1 對應裝置的電源管理設定、轉接器型號與驅動版本 | 維運 | COM1 專屬的系統層因素 |
| 刷卡機端的 ECR 通訊設定（速率／同位／資料位元），以及店員失敗後怎麼再刷 | 維運／店員 | 確認設定沒被重設、評估重複扣款 |
| 發病當天的 Ragdoll `logs/main` | 門市（已輪替就拿不到） | 發病當時版本與啟動事件；**下次先請門市保存** |
| 對調測試結果 | 維運 | 定位線材／接頭／COM 埠／刷卡機 |

## Step 7：產出

報告骨架與維運文案模板見 `references/report-template.md`：

- **調查報告**：存成 `.md`（使用者指定的位置優先；沒指定就用 `~/Downloads/<門市>-<機台>-刷卡機通訊異常調查報告.md`），**不放進 repo、不 commit**，除非使用者要求。
  **若由子代理執行而環境不允許寫檔**，把報告全文放在回覆裡交給呼叫者存檔，不要改用 Bash 繞過限制。
  必含信心表、已證明／推論／未知、限制與尚未驗證、更正紀錄（說錯又修正的如實列出）。
- **維運文案**：白話，不放技術名詞；使用者要求「只講 COM Port 傳輸漏傳」時用版本 B。
- 回覆使用者：先給初判與信心，再給證據、未知、下一步；建議的工程項目（如代理程式補失敗警告、離線卡號只收末四碼）
  只當建議，**是否開票由使用者決定**。

## 常見陷阱（完整清單見 `references/pitfalls.md`；校準數字見 `references/worked-example-090-09011.md`）

1. ECR 設定檔是 `ecr/CS_ecr.dat`（修改時間每次更新），不是根目錄 `config.ini`。
2. `0001`／`0003` 在規格書回應碼表（Error／Timeout）；`CS_ErrorCode.dat` 是細項碼表。細項碼空白才是通訊層。
3. 回應碼在資料 `[78:82]`；ACK 是連續兩個 `0x06`；`ErrRec Message [NN]` 的 `[NN]` 是長度不是錯誤碼。
4. 同一區塊兩個 403 bytes 結果框只差 `Transaction finished` 與 `Timer block reset` ＝電子簽名多段流程，不是重送。
5. 「沒有變更」≠「沒有 bug」：寫「未發現證據」，並逐項檢驗潛伏假設。
6. 手 KEY 筆數是代理指標且是下限；個位數是背景雜訊。
7. 「核准後仍手 KEY」要金額相同且該核准沒入帳才算疑點，只看時間會誤報。
8. `COM3 外部要求釋放（/release）` 是 Ragdoll 每次開機的例行呼叫，不是故障觸發點；`detectTsbSubtype 3 秒無回應` 也是正常。
9. 代理程式不把台新失敗記成警告，要解碼 out.dat 看；COM3 健康只代表共用部分健康。
10. 電腦名稱與機台編號可能不一致；「同在種子名單」不等於「同版本」。
