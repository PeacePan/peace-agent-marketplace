# 判定決策樹：程式問題 vs 硬體線路問題

這份文件回答一個問題：**門市說「刷卡機刷成功、POS 顯示失敗」，證據該怎麼組織，才敢說是程式還是線路。**

## 1. 先把呼叫鏈拆成層，再逐層找「第一個壞掉的地方」

```
① Ragdoll（Electron／Next）
② ─ HTTP ─▶ POSAgentDotNet 代理程式（種子名單內的機台；否則 Ragdoll 直連，跳過 ②）
③ ─ 寫 in.dat、執行 ─▶ ECR.exe（台新中介）
④ ─ COM1，115200 8N1 ─▶ 刷卡機（EDC）
⑤ 刷卡機 ─▶ 銀行主機
```

| 層 | 這一層「正常」長什麼樣（證據在哪） | 這一層「壞」長什麼樣 |
|---|---|---|
| ① Ragdoll | 收到代理程式的結果後正確顯示；無重送；pilot 模式不預檢 | 結果是核准（0000）卻顯示失敗；請求內容（金額、欄位）錯誤 |
| ② 代理程式 | 每筆 `in.dat 已寫入 → out.dat 讀取完成` 成對；版本與訊息型態前後不變；無 `DeviceFaulted` | 有 in 沒 out、新的 WRN／ERR、版本或重啟與發病吻合、閂鎖暫停刷卡 |
| ③ ECR.exe | log 區塊乾淨、每次一個 START…END；沒有殭屍（區塊重疊或區塊外殘留） | 區塊重疊、殘留輸出、`out.dat` 被舊內容覆蓋 |
| ④ 序列線路 | 送出後 <1 秒收到 `0606`；結果框 403 bytes、LRC 正確 | **無回應**（`[16]`）、**亂碼／多餘垃圾／零星雜訊**（`[17]`）、等不到結果（`[14]`） |
| ⑤ 刷卡機／銀行 | 完整結果框，回應碼 `0000` 或帶細項碼的拒絕 | 回應碼非 `0000` 且細項碼有值（客戶、授權、操作） |

**「第一個壞掉的層」＝故障層。** 本 SOP 的結論形式永遠是「故障在第 N 層，證據是…，信心是…」。

## 2. 證據矩陣：每項證據能排除什麼

| 證據 | 怎麼取得 | 能排除／支持什麼 |
|---|---|---|
| **發病點與變更是否吻合** | `triage.py` 的發病日；git tag 日期；代理程式版本／重啟；種子名單生效日 | 無變更吻合 → 排除 regression；有吻合 → 優先懷疑該變更 |
| **對照組** | 中台：同店他機、他店同期的正常刷卡 vs 手 KEY 比例 | 他機正常 → 排除全店／銀行／中台；多機同時壞 → 偏共同原因（版本、更新、環境） |
| **請求封包前後相同** | ECR log `Send Message [400]` 發病前後逐字比對 | 相同 → ① 與 ② 送出去的內容沒變 |
| **ACK 後結果損壞** | `ACK_THEN_BAD` 次數 | 刷卡機**已收下請求**（POS→刷卡機方向至少那次是通的），壞的是回程 |
| **損壞型態** | 損壞封包的長度（多於或少於 403）、高位元組比例、同期是否有乾淨框 | 見下一節 |
| **歸檔 out.dat 範本** | 空白＋`0001`／`0003`、細項碼是否為空 | 細項空白＝中介沒收到完整回覆（通訊層）；細項有值＝刷卡機回報的具體原因（非通訊層） |
| **代理程式 log** | 每日 out.dat 解碼、訊息型態前後比對、版本與重啟時間軸 | 無異常 → 排除 ②；它不記失敗警告，**不能因為沒有 WRN 就當正常，要看解碼結果** |
| **COM3 發票機探針** | `printer-serialdata-*.log` 的 `DLE EOT` 回應延遲與缺失 | 全程健康 → 排除 PC 負載、作業系統、USB 主機這些共用部分（但不代表 COM1 的轉接器健康） |
| **調閱編號對帳** | 成功交易的 `receipt_no` 缺口 vs 手 KEY 筆數 | 兩者吻合 → 每筆「POS 失敗」刷卡機端都有交易；**但仍要以刷卡機結帳單核實是否扣款** |
| **區塊完整性** | ECR log 是否每次都是乾淨的 START…END，區塊外有無殘留輸出 | 有重疊或殘留 → 殭屍 `ECR.exe` 或兩個程序搶 COM1（偏程式／系統層） |
| **請求樣板** | 遮蔽調閱編號、金額、日期時間、櫃機號時戳後，發病前後的請求是否同一種 | 一致 → ①② 送出的內容沒變；發病後出現新樣板 → 送出的格式變了（偏程式） |
| **NAK 次數** | ECR 送給刷卡機的 `<Nak><Nak>` 發病前後各幾次 | 發病後才出現 → ECR 收到損壞結果並要求重送（佐證回程損壞） |
| **重試風險** | ACK 後損壞、同金額重試核准的調閱編號是否連號 | 連號 → 失敗那次沒佔用編號（無重複扣款跡象）；有缺口 → 要對結帳單 |
| **手 KEY 的前因** | 每筆手 KEY 前 10 分鐘內有無金額相符的失敗 ECR 呼叫 | 都有 → 手 KEY 確實是因通訊失敗；找不到的要逐筆看（分次付款或沒先刷就手 KEY） |

## 3. 損壞型態怎麼讀（區分「線路雜訊」「速率不符」「接收端丟位元組」）

| 觀察 | 解讀 | 為什麼 |
|---|---|---|
| 損壞封包**多於** 403 bytes，或只收到 1～16 bytes 的高位元組雜訊（`FE FF`…） | **間歇性接觸不良／線路雜訊** | 接收線上出現「不是刷卡機正常送出」的資料；接收端 overrun 只會丟位元組，不會多出垃圾 |
| 同一時段，**乾淨的 403 bytes 框**夾在損壞封包之間 | **不是靜態設定不符** | 速率、同位、位元數設定錯誤會讓「每一筆」都壞，不可能偶爾傳出乾淨的框 |
| **全部**都是亂碼、**沒有任何乾淨的框** | **靜態速率／格式不符** | 請核對兩端的 baud／parity／data bits（刷卡機 ECR 通訊設定可能被重設） |
| 只有**縮短**的框、**沒有**多餘垃圾，且 COM3 探針同時變慢或缺失 | **接收端丟位元組（overrun）／PC 負載／轉接器驅動** | 丟位元組是接收端來不及處理的特徵；用 COM3 探針驗證 PC 是否整體變慢 |
| **完全沒收到**任何位元組（`[16]`，占大宗） | 無法由 POS 端分辨「請求沒到」或「回覆沒回來」 | 看有沒有「ACK 後損壞」的案例（證明至少回程有問題）；其餘靠現場看刷卡機「POS 觸發刷卡時是否自動帶出金額」 |

## 4. 初判規則（triage.py 實作的邏輯，人工判讀時照此檢查）

1. **沒有 ECR log** → 無法判定，請門市重送回報包。
2. **ECR 通訊失敗率低、無發病點，但有多筆「金額相同、5 分鐘內、且該核准沒有對應入帳」的手 KEY**（≥3 筆）→ 疑似程式／流程（刷卡機核准了，POS 卻沒認）。只看時間會誤報。
3. **刷卡機有完整回覆、回應碼非 `0000` 的次數多於通訊失敗** → 刷卡機端（拒絕、取消、操作），不是線路；讀細項碼。
4. **通訊失敗率高（發病後 ≥ 50%）且有發病點** → 預設「硬體／線路」，再用下列項目調整：
   - 封包鑑識呈現雜訊／接觸不良特徵 → 信心 +1
   - 代理程式 log 無異常（無新 WRN／ERR、無版本變更、in／out 成對、無閂鎖） → 信心 +1
   - **任何一項程式疑點 → 改判「有程式或系統層疑點」並降信心**：代理程式新的警告／錯誤訊息類型、版本在發病前後 3 天內變更、`DeviceFaulted`、in／out 數量不一致、COM3 探針同時變差、種子名單生效日與發病日相差 3 天內
5. **信心上限**：沒完成「排除程式變更（Step 3）」與「中台對照組（Step 4）」且沒有代理程式 log，最高只能「中高」。三者都到位才能寫「高」。

### 信心等級的意思

| 等級 | 意思 | 可以怎麼對外說 |
|---|---|---|
| 高 | 程式變更已排除、同店對照機台正常、代理程式 log 已檢視無異常、封包型態一致 | 「故障在序列通訊層，請現場檢修」 |
| 中高 | 證據一致，但缺其中一項確認 | 「高度疑似線路，另有 X 項待確認」 |
| 中 | 只有 ECR 層的證據 | 「疑似線路，但還不能排除程式」 |
| 低 | 資料不足或有未排除的程式疑點 | 「無法判定，需要補資料」 |

## 5. 「硬體」內部怎麼再縮小（現場對調測試）

線材、接頭、轉接頭、COM1 埠硬體（或其 USB 轉接器）、刷卡機該埠的收發器，這幾項產生的症狀相同，**資料無法區分**，只能對調：

| 做法 | 結果 | 結論 |
|---|---|---|
| 用同店正常機台的傳輸線換到故障機台 | 變好 | 線材或接頭壞（連同轉接頭） |
| 把兩台刷卡機對調 | 問題**跟著刷卡機走** | 刷卡機（或其設定／該埠） |
| 把兩台收銀機的轉接器／COM 埠對調 | 問題**跟著轉接器走** | 轉接器或其驅動 |
| 以上都沒改善 | — | 收集 COM1 專屬的系統層資料：事件檢視器（序列埠、USB 轉接器相關）、裝置管理員的電源管理（是否允許電腦關閉此裝置以節省電源）、轉接器型號與驅動版本、發病夜間的 Windows／驅動更新 |

**驗收標準**：連續 10 筆小額刷卡 POS 皆顯示成功；當天 ECR log 無 `[14]`／`[16]`／`[17]`；代理程式 log 的 out.dat 以 `11` 開頭。
對調測試會暫時影響正常機台，建議離峰並先告知店長。

## 6. 什麼情況要改判成「程式問題」

| 訊號 | 為什麼 |
|---|---|
| ECR 回應碼 `0000`（核准），POS 卻顯示失敗、店員仍手 KEY | 刷卡機與線路都沒問題，問題在 ①②（逾時、狀態判斷、結果解析） |
| 發病日與 Ragdoll 版本、代理程式更新／重啟、種子名單生效、設定變更吻合 | 優先懷疑該變更 |
| 同期同版本的多台機台同時開始失敗 | 偏共同原因，不像個別線材 |
| 代理程式 log：`DeviceFaulted`、新的 WRN／ERR、in 與 out 數量不一致 | 代理程式層異常 |
| ECR log：區塊重疊、區塊外殘留輸出 | 殭屍 `ECR.exe` 或雙程序搶 COM1 |
| 發病後請求樣板出現發病前沒有的新樣板 | 送出的格式或內容變了 |
| 發病前後請求封包內容不同（欄位、金額、格式） | 送出的內容變了 |
| COM3 探針與 COM1 同時變差 | 系統層（CPU、USB、驅動）而非單一線路 |
| 錯誤是帶細項碼的 `0001`（01XX～07XX） | 刷卡機回報的具體原因，是客戶、銀行或操作，不是線路 |

## 7. 結論的寫法

- **不要寫「排除」**，除非有正向證據。證據只支持「沒有 regression、沒有處理錯誤」時，寫「未發現證據」。
  「沒有變更」不等於「沒有 bug」，潛伏缺陷可能在新的環境條件下才被觸發。
- 分三類寫：**已證明**（附證據）、**推論**（附推論依據與驗證路徑）、**未知**（附如何查）。
- 「刷卡機都已扣款」是超出證據的說法；寫成「刷卡機端皆有對應交易編號，是否扣款需以結帳單核實」。
