# 踩雷清單與典型案例

這些都是真實調查（090 青年店 09011，2026-10）過程中**說錯或差點說錯**、事後用證據更正的事。
每一條都附「怎麼避免」，照做可以省下重工。

## A. 讀檔與欄位

1. **ECR 設定檔是 `ecr/CS_ecr.dat`，不是回報包根目錄的 `config.ini`。**
   根目錄的 `config.ini` 是 Ragdoll 自己的設定（`TSB_COM`、`TSB_BAUDRATE=9600`、even、7…是直連與開機探測用）。
   而且 `CS_ecr.dat` 的修改時間**每次交易都更新**，所以「設定檔 X 月 X 日沒動」這種論據不成立，
   只能說「目前內容符合規格書通訊參數，發病前後是否變動無法確認」。
2. **`0001`／`0003` 在規格書的回應碼表裡**（`0001` Error、`0003` Timeout），不是什麼「ECR 自己的碼」。
   `CS_ErrorCode.dat` 是**細項碼**表，查不到 `0001` 是正常的。
3. **回應碼位置是 1-based 79～82，也就是資料 `[78:82]`**。從含 STX 的 403 bytes 封包切要再 +1。
   切偏一格會把端末機代號的第一碼讀進來（成功碼 `0000` 被誤讀成 `0006`）。
4. **`ErrRec Message [NN]: …` 的 `[NN]` 是損壞資料的長度，不是錯誤碼。** 只有「中介程式執行錯誤 [NN]」那一行才是 ECR 的錯誤碼。
5. **單獨一個 `0x06` 不是 ACK**，ACK 是連續兩個（`0606`）。
6. **同一區塊出現兩個 403 bytes 的結果框、只差 `Transaction finished`（`N`→`Y`）與 `Timer block reset`（`0250`→`0000`）等幾個位元組，
   是電子簽名的多段流程，不是「刷卡機重送」**。我曾把它當成「8/11 起的預兆」，比對差異後推翻。
   見到「重複」先 diff 兩個框，不要憑印象下結論。
7. 「正常一次呼叫收到 2 筆回應」只對**非簽名**交易成立；簽名交易會多一個結果框。
8. **ECR log 是 Big5**：用 `iconv` 遇非法位元組會截斷。解析請用位元組（`latin-1` 看 hex，`cp950` 解中文行）。

## B. 判斷與措辭

9. **「沒有變更」≠「沒有 bug」。** 證據只支持「沒有 regression、沒有處理錯誤」時，寫「未發現證據」，不寫「排除」。
   潛伏缺陷可能在新的環境條件下才被觸發；要逐項檢驗（殭屍程序、COM1 搶用、overrun、速率不符），不要停在「需要現場」。
10. **資料能查的就先查完，再說「需要現場」。** 這次的封包鑑識與 COM3 探針，一開始都被我放進「未排除」，
    被追問後才做，結果直接把「PC 負載」「速率不符」兩個假設推向不利。
11. **不要說「每筆 POS 失敗，刷卡機都已核准扣款」。** 調閱編號對得上只證明刷卡機端有對應交易；
    是否核准、是否扣款，以刷卡機結帳單為準。10/03 之後沒有成功交易，編號無法再對帳。
12. **「同在種子名單」≠「同版本」。** 對照機台的 Ragdoll、代理程式、ECR 版本要逐機核對，沒核對就明說「未查證」。
13. **手 KEY 筆數是代理指標，而且是下限**（漏掉「失敗後重刷成功」，也含正當離線使用如銀聯卡）。
    PM 說「多間店都有」時，**逐機台算比例**，不要只回「有手 KEY」。
14. 初判「走直連還是代理程式」要看證據（種子名單＋本機設定＋發票機 log 有無「POSAgentDotNet open/print 成功」），
    **不要憑印象**。我曾說「09011 還走舊的直連路徑」，結果是錯的。

## C. 工具與資料

15. **中台 `summarize` 帶 `lineFilters` 並行會全部 `fetch failed`**；單發依序可用。`count` 並行無礙。
16. **美容單（`sale_kind=SERVICE`）在中台 `posservicesale`**，本機手 KEY 筆數對不上 `possale` 時先查這張。
17. **代理程式不把台新失敗記成 WRN／ERR**，只在 INFO 貼 out.dat 的 hex。看 WRN／ERR 沒東西不代表正常，要解碼 out.dat。
18. **COM3（發票機）健康只代表共用部分（CPU、作業系統、USB 主機）健康**，不代表 COM1 的轉接器或硬體健康。
19. **電腦名稱與機台編號可能不一致**（本案電腦名稱與代理程式 StoreId 是 `POS09001`，機台編號是 `09011`）。
    交易時間與金額可以和 ECR log 逐筆對上來確認是同一台；現場請對方以 Ragdoll 畫面上的機台編號為準，不要認電腦名稱。
20. 回報包的 Ragdoll log 只保留約 3 天，發病當天的 Ragdoll 端紀錄常已被輪替。下次先請門市保存或趕快索取。
21. 本機 SQLite 以唯讀開啟（immutable），不要在下載資料夾內執行直譯器，不要輸出卡號；
    歸檔 out.dat 與 `reconcile_info` 只統計格式，不印內容。
22. **「核准後仍手 KEY」只看時間會誤報。** 要「金額相同、5 分鐘內、且該核准沒有對應的 CREDIT 入帳」才算疑點。
    曾把「核准的是 NT$99（已入帳）、手 KEY 的是之後另一筆 NT$352」誤報成程式疑點。
23. **「請求封包逐字相同」做不到**：調閱編號、金額、日期時間、機台時戳每筆本來就不同。要先遮蔽這些欄位再比樣板（腳本已做）。
24. **`COM3 外部要求釋放（/release）` 是 Ragdoll 每次開機的例行呼叫**（約每天 10:40～10:58），不是故障觸發點；
    服務停止時的「釋放序列埠」同理。看到它落在「最後正常」與「首次失敗」之間時，先查歷史頻率再下判斷。
25. **開機的 `detectTsbSubtype: 3 秒無回應，判定為 TSB_ECR（400-byte 裝置）` 是正常的**（400B 刷卡機本來就不回應 144B 探測）。
    Ragdoll 開機會用 `config.ini` 的 9600／even／7 對 COM1 送一個探測封包，每天、每台都做，發病前也有，**不是發病的差異因素**；
    但它對刷卡機的殘留影響沒有直接驗證，只能寫成「已檢驗為不利、未直接驗證」。
26. **由子代理執行本 SOP 時，環境可能不允許寫 `.md` 報告**：把報告全文放在回覆裡交給呼叫者存檔，不要用 Bash 繞過。
27. 重複扣款風險不能只說「靠結帳單」：用「ACK 後損壞、隨後同金額重試核准」的調閱編號是否連號先評估（腳本 1.4 表），
    並問店員失敗後是在 POS 再刷還是在刷卡機上單機再刷。

典型案例的校準數字見 `worked-example-090-09011.md`。
