# 診斷報告與維運文案模板

兩份產出對象不同，**不要混成一份**：

| 產出 | 讀者 | 重點 | 語氣 |
|---|---|---|---|
| 調查報告（本檔 §1） | 工程師、PM、主管 | 證據、判定、信心、未知 | 技術但誠實，分「已證明／推論／未知」 |
| 維運文案（本檔 §2） | 維運、門市、店長 | 哪台壞、現場做什麼、怎樣算修好 | **白話**，不放技術名詞 |

報告存成 `.md` 放使用者指定的位置（預設 `~/Downloads/<門市>-<機台>-刷卡機通訊異常調查報告.md`），
**不要放進 repo、不要 commit**，除非使用者要求。

## 1. 調查報告骨架

```markdown
# <門市> <機台> 刷卡機通訊異常調查報告

| 項目 | 內容 |   ← 門市／機台、環境與版本、問題回報事件代碼與時間、門市描述、調查日期、資料截止時間、調查性質（唯讀）

## 1. 摘要           ← 故障位置、發病時間、惡化過程、直接證據、對照組、帳務、建議；再加「信心等級」表
## 2. 資料來源       ← 回報包、代理程式 log、中台查詢、程式碼、規格書
## 3. 呼叫鏈與正常流程   ← 圖
## 4. 調查方法（摘要）
## 5. 調查發現
   5.1 發病時間點
   5.2 通訊層證據（ECR log：逐日、失敗型態分類、「ACK 後損壞」的直接證據、區塊完整性、請求樣板、NAK、重試風險檢查）
   5.3 回應封包的規格書解讀（失敗範本 vs 成功封包的欄位對照）
   5.4 帳務對帳（調閱編號缺口、手 KEY 規模、上傳狀態、重複輸入檢查、預估目前編號）
   5.5 單機對照與發病前基準
   5.6 排除軟體因素（版本 tag 日期、模組 diff、請求封包相同、ECR 設定）
   5.7 種子名單與代理程式 log
   5.8 其他門市（若被問到）
   5.9 損壞封包鑑識與 PC 序列系統健康檢查（COM3）
## 6. 假設與排除（表）＋ 6.1 軟體假設的檢驗（已檢驗／仍無法查證）
## 7. 建議行動        ← 維運（現場）、門市與財會、觀察與蒐集、工程（僅建議，是否開票由負責人決定）
## 8. 附帶發現（非本次故障原因）
## 9. 限制與尚未驗證
## 10. 調查過程中的更正紀錄   ← 說錯又修正的，如實列出
## 附錄 A 給維運的白話文案／B 規格書重點對照／C 重現方法
```

寫作規則：

- **信心表必寫**，且至少分三列：故障層（高）、軟體無關（中高或高，視確認項）、具體是線材／接頭／COM 埠／刷卡機（未知）。
- 每個數字註明來源與統計口徑（ECR log 呼叫次數、代理程式 log 次數、本機筆數、中台筆數口徑不同，會差 1～3）。
- 「未驗證」一定要列，**不寫「排除」，寫「未發現證據」**（見 decision-tree.md §7）。
- 不輸出卡號、授權碼、完整員工姓名；回報人用員編即可，要對外轉傳前提醒使用者確認。
- 附帶發現（如離線刷卡存了完整卡號、代理程式不記失敗警告、ECR 版本過舊或逾時設定偏短、電腦名稱與機台編號不一致）
  只描述事實與影響，**不自行建票**，由使用者決定。

## 2. 維運文案模板

### 2.1 版本 A：現場檢修請求（有步驟）

```
【請派人到 <門市名> 檢修】<機台> 收銀機的刷卡機連線異常

狀況：<機台> 收銀機刷卡時，店員反映刷卡機已經刷成功，但收銀機沒收到結果，畫面顯示「刷卡失敗」，店員只好手動補登。
影響：<發病日> 起到現在，約 <N> 筆、約 <金額> 元都是手動補登。同一間店的 <正常機台> 正常，只有 <機台> 這台有問題。
原因：<上一次正常日> 還正常，<發病日> 突然開始，我們查過紀錄，這段期間沒有看到軟體更新或設定被改的跡象。最可能是收銀機和刷卡機之間的連接線鬆了、壞了，或接頭、轉接頭、刷卡機上對應的接孔有問題。

請現場處理
1. 把 <機台> 收銀機和刷卡機之間的連接線（收銀機後面標示 COM1 的那個接孔）兩端重新插緊，看接頭有沒有鬆動、歪斜或損壞。
2. 刷卡機和收銀機都重新開機。
3. 還是不行，就拿 <正常機台> 的連接線換到 <機台> 試刷：變好代表線壞了，直接換新；沒變好再把兩台刷卡機對調試刷。
4. 問店員 <上一次正常日> 晚上到 <發病日> 早上，有沒有搬動設備、停電、刷卡機換機或更新。

怎樣算修好：<機台> 連續刷 10 筆小額，收銀機都顯示成功。
修好之前，門市先照目前做法手動補登，並保留刷卡機的結帳單，之後對帳要用。
```

注意：步驟 3 的對調會暫時影響正常機台，建議離峰並先告知店長（寫在給維運的回覆裡，不必放進文案）。

### 2.2 版本 B：只解說「COM Port 傳輸漏傳」（使用者要求只講這部分時）

```
收銀機和刷卡機之間靠一條傳輸線（接在收銀機後面標示 COM1 的接孔）來回傳資料，像兩個人在對講。<上一次正常日> 以前這段對話每次都完整，<發病日> 起傳回來的資料開始遺失或損壞。

正常的對話：
收銀機 ──「這筆要刷 1,500 元」──▶ 刷卡機
收銀機 ◀──「收到了」────────── 刷卡機
        （客人刷卡，約 6 秒）
收銀機 ◀──「刷卡完成，核准碼…」── 刷卡機
收銀機 ──「收到了」──▶ 刷卡機      → 畫面顯示成功

現在的情況：<發病日> 起收銀機共送出 <N> 次刷卡請求——
| 發生什麼事 | 次數 | 畫面結果 |
| 完整收到結果 | <a> | 成功 |
| 完全沒收到任何回應：送出後等 2 秒沒回，重送一次還是沒回，就放棄 | <b> | 刷卡失敗 |
| 只收到殘缺或亂碼的資料 | <c> | 刷卡失敗 |
| 「收到了」有回來，但結果在傳回來的途中壞掉（應 403 字元只剩 <x> 字元，後半段變亂碼） | <d> | 刷卡失敗 |

意思是：收銀機送出去的內容前後一致，只有「收回來的資料」開始遺失或損壞；這是兩台機器之間的訊號傳輸出了問題，不是軟體算錯。
這種時好時壞、越來越糟的模式，常見於接頭鬆動、傳輸線劣化，或兩邊的傳輸設定不一致。
```

### 2.3 聊天版（3 行）

```
<門市> <機台> 的刷卡機「刷成功但收銀機顯示失敗」，<發病日> 起已有約 <N> 筆手動補登。同店 <正常機台> 正常，沒看到軟體更新的跡象，疑似收銀機到刷卡機的連接線或接孔異常。請派人現場：重插連接線兩端、兩台重開機、用 <正常機台> 的線換到 <機台> 試刷。修好標準：連續刷 10 筆都顯示成功。
```

### 文案用語規則

- **不用技術名詞**：不寫 ECR.exe、ACK、POSAgentDotNet、調閱編號、`0001`、LRC、baud、「COM1 埠」。需要時改成「收到了」「確認」「傳輸線」「連線設定」「收銀機後面標示 COM1 的接孔」。
- **不下超出證據的斷言**：不寫「客人也扣款了」（寫「店員反映刷卡機已刷成功」）、不寫「沒有任何軟體更新」（寫「查過紀錄沒看到更新或設定被改的跡象」）、不寫「不是軟體問題」。
- 數字全部來自 `triage.py`（發病日、次數、金額）；金額寫「約」。
- **不寫「客人都已扣款」**：寫「刷卡機端有對應交易」或「刷卡機已刷成功」，是否扣款以結帳單為準。
- 「只有這台」的說法要有中台對照組支撐（Step 4）；沒做就不要寫。
- 如果初判不是「線路」（見 decision-tree.md §6），**不要用這份文案**，改寫對應的處理方向。
