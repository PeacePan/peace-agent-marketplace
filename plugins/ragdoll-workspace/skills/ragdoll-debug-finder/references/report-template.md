# 根因報告模板、判定表與開卡欄位對照

## 判定結果

| 判定 | 成立條件 | 後續 |
|---|---|---|
| 程式缺陷 | 因果鏈完整、確實違反預期、最新已發版版本仍存在 | 進 Step 6 詢問是否開卡 |
| 已修復待更新 | 缺陷存在於回報版本，且較新的 `ragdoll-v*` tag 已含修復 | 報告列出修復所在的 tag，請維運安排門市更新；不開卡 |
| 資料或設定問題 | 程式行為正確，是中台主檔、促銷或門市設定造成 | 報告指出是哪筆資料或設定、該由誰處理；不開 bug 卡 |
| 操作問題 | 符合 `ragdoll-user-manual` 描述的正確操作 | 報告附上可回覆門市的白話說明 |
| 環境或硬體 | 網路、機台時鐘、周邊設備等 | 報告列出證據；刷卡機改走 `ragdoll-card-reader-triage` |
| 資訊不足 | 因果鏈有缺口 | 列出缺口與要向門市追問的內容，由使用者決定是否再追 |

「沒有找到證據」不等於「沒有 bug」，證據只支持「未發現問題」時，結論寫「未發現證據」，不寫「排除」。

## 報告格式

直接輸出在對話中，依序包含以下段落：

```
# 門市回報分析：<一句話現象>

**結論**：<判定>（信心：高／中／低）

## 1. 門市回報
環境、版本、門市、機台、回報時間、代碼；門市原話：「…」

## 2. 現象與證據
每一條標示（已證明）或（推論），並指出來源：檔案、表名與單號、日誌時間、行號。

## 3. 根因
用「A → B → C」寫出因果鏈，每一環附程式碼位置（`Ragdoll/<路徑>:<行號>`，tag 為 ragdoll-v<版本>）。

## 4. 影響範圍
受影響的版本與門市、已發生的筆數、對帳務或顧客權益的後果、門市有沒有繞過方式。

## 5. 最新版狀態與既有卡片
最新 ragdoll tag 是否已修；Jira 上是否有相似的未結案漏洞卡。

## 6. 建議修法方向
只寫方向與要改的位置，不實作。

## 7. 信心與未知
| 項目 | 證據等級（已證明／推論／未知） | 要補的驗證 |

## 附錄
解壓資料夾路徑、中台檔案記錄連結（🔗 來源）。
```

寫作規則：會員姓名、手機一律用單號或編號代替；每個結論都能回溯到一個具體證據；推論必須寫出驗證方法。

## 嚴重度判讀（用來說明影響，不代替使用者決定）

詢問優先度時，把下列面向轉成這個 bug 的具體事實，放在選項說明裡：

| 面向 | 要說清楚的事 |
|---|---|
| 影響面 | 單一機台、單店、多店、所有門市 |
| 後果 | 帳務或金額錯誤、顧客權益受損（次數、點數、包月）、資料遺失或重複、只是顯示或體驗不佳 |
| 頻率 | 每次必現、特定條件才出現、偶發 |
| 繞過方式 | 門市有沒有辦法自行避開或補救 |
| 已造成的資料 | 是否已有需要事後修正的紀錄、大約幾筆 |

Jira 優先序由高到低為 Urgent、Highest、High、Medium、Low、Lowest；漏洞卡的預設值是 High，但這個預設不能拿來代替詢問。

## 開卡欄位對照（漏洞 issuetype 10008）

| 欄位 | 寫什麼 |
|---|---|
| 摘要 | `[Ragdoll] <現象>`，用業務語言 |
| 描述 | 問題是什麼、對誰有什麼影響、何時發生、門市原話（去除個資）、目前造成的後果。不寫路徑、函式名、程式碼 |
| 正確行為（customfield_10059） | 修好之後系統應該怎樣運作 |
| 驗收條件（customfield_10030） | checkbox 清單，每條是「操作 → 預期結果」，驗收者可照著做 |
| 討論紀錄（customfield_10266） | 工程細節：根因、程式碼位置、證據、回報版本、回報代碼、🔗 來源 |
| 優先度 | 使用者在 Step 6 的選擇 |
| Parent（Epic） | `RD-7600`（Ragdoll POS-R）。`ragdoll-acceptance-workflow` 只驗收父系 Epic 為 RD-7600 的卡，沒掛上之後就無法被實機驗收；使用者另有指定時以使用者為準 |
| 上線版本（customfield_10038） | 留空（尚未修復） |
| 標籤 | 不加。HOTFIX 等標籤會改變分支與發版流程，使用者沒指示就不自行決定 |

自訂欄位（正確行為、驗收條件、討論紀錄）都不接受 markdown，必須是 ADF 物件；ADF 範本與建立流程以 `wonderpet-general:jira-create-issue-rule` 和 `wonderpet-general:jira-overview` 為準。
