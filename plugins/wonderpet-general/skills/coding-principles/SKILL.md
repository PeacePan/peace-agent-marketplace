# 程式碼撰寫與重構準則

整合圖卡「用 AI 重構程式碼 100 招」（共 4 張，原圖出處：東大 Codex 研究所）。圖卡本身是 100 個招式的清單；這份 skill 在清單之外補上「怎麼用」：先界定範圍與保護網，再用異味找出問題，最後挑對的招式小步執行。

## 先記住三件事

1. **重構是不改變外部行為、只改善內部結構。** 一旦同時改了行為，就沒有人能判斷「壞掉是整理造成的，還是功能改壞的」。所以結構整理與行為變更要分開做、分開驗證。
2. **100 招是工具箱，不是檢查表。** 每一招都有適用條件，而且有互相拉扯的反向招式（抽取對內聯）。選招的標準是「讀的人會不會更容易理解、改的人會不會更不容易出錯」，不是「有沒有套用招式」。
3. **範圍只限這次要動的程式碼。** 順手發現的範圍外異味，回報就好，不要順手改。否則 diff 變大，審查者無法把每一行改動對回需求，行為變更也容易混進整理裡。

## 兩種使用方式

- **診斷模式**：使用者問「哪裡該重構」「幫我看看這段有什麼異味」「review 一下」。只回報，不改檔：列出位置、異味編號與名稱、為什麼是問題、建議的招式。
- **執行模式**：使用者說「重構這段」「用 #51 改寫」「把這個函式拆開」，或直接念圖卡原句（例如「找出過長的函式，用『抽取函式』把它們拆開」）。依下面的流程改檔。

使用者可能用編號（`#26`）、招式名稱，或圖卡原句指定招式。各招的圖卡原句收在 references 裡，認得它就知道該走哪一招。

## 工作流程（執行模式）

### Step 1：界定範圍

以這次的要求為界，只處理要新增或修改的函式與檔案。使用者明確要求「重構整個模組」時，範圍就是該模組，但仍要分小步。範圍外看到的異味，記下來等最後回報，不要動。

### Step 2：建立保護網（修改既有程式碼時）

保護網決定你敢走多大步，所以動手前先確認它存在：

- 受影響範圍已有可執行的測試：先跑一次確認基準是綠的。基準本來就是紅的，要告訴使用者，不要默默往下做。
- 沒有測試：寫特徵測試（76）把現狀鎖住；輸出龐大難以逐欄斷言時，用黃金樣本（99）。用覆蓋率（90）確認要動的分支真的被測到。
- 實在無法自動驗證（純版面、環境跑不起來）：明講「沒有自動化保護網」，縮小步伐，改靠型別檢查與 lint 把關，不要假裝有驗證過。

純新增程式碼不需要這一步，改看下一節的預設姿勢。

### Step 3：診斷

用下面的「異味速查表」把症狀對到異味與招式編號，再到對應的 references 讀該招的做法與注意事項。一次只選一個異味、一招；同時處理多個，出錯時就分不清是哪一步造成的。

### Step 4：小步執行

一次只做一種改變（改名、搬移、抽取三者擇一），每步之後跑型別檢查、lint 與相關測試（77、78）。某一步失敗就退回上一步再查，不要在壞掉的基礎上繼續。格式化（87）與 lint 修正（86）一律用專案既有工具。

### Step 5：收尾自我檢查

- 外部行為沒變：測試全綠，型別檢查與 lint 沒有新增警告。
- 每個改動都能對回一個異味與一個招式。對不上的多半是順手改，退回去。
- 沒有製造新異味：新抽出的函式參數會不會太多？新加的抽象有沒有第二個使用者？
- 範圍外的程式碼沒被動到。

### Step 6：回報

```
## 重構摘要
- 範圍：<檔案或函式>
- 保護網：<既有測試／新增特徵測試／黃金樣本／無（原因）>
- 使用的招式：<#編號 名稱：改了什麼>
- 驗證：<型別檢查、lint、測試的實際結果>
- 範圍外發現（未處理）：<位置：異味 #編號>
```

## 新寫程式碼時的預設姿勢

新增功能時沒有舊行為要保護，但同樣的原則要從一開始就守住，比事後重構便宜得多：

- 先想好名稱再寫；名稱看不出用途就重取（03、27、97）。
- 函式只做一件事，能一句話說完；超過一個螢幕就拆（01、26、79）。
- 例外與不適用的情況先 return，巢狀不超過三層（04、51）。
- 字面值具名（05）；狀態用列舉或聯合型別（67）。
- 參數不超過 3～4 個，成組的值包成物件（07、33）；不用布林旗標切換行為（34）。
- 計算與副作用分開：能寫成純函式就寫純函式（94）；查詢與更新分開（35）；資料預設不可變（95）。
- 外部輸入在系統邊界驗證（62），型別寫清楚（91）。
- 時間、網路、資料庫這類外部相依從參數進來，才好測試（93）。
- 只做目前需要的（81、82）；等第二個使用者出現再抽象（20、100）。

## 取捨：招式之間會互相拉扯

遇到下列情況時，不要憑直覺套招，照這裡的判準選：

- **抽取對內聯**（26、29、30、46 對 31、39、45、44）：判準是「名稱是否比本體更好懂」。抽出後名稱沒有增加資訊，或只用一次且很短，就內聯。
- **一般 if 對多型、策略、狀態、查找表**（54、60、61、68）：分支少且穩定，保留 if 或 switch。單純 key 對映用查找表（60）。同一組分支在多處重複出現（16）或預期持續增長，才升級成多型、策略或狀態模式。
- **三元運算子對守衛子句**（63 對 51）：三元只用在單層的「挑一個值」。巢狀三元一律改回 if 或守衛子句。
- **快速失敗、斷言對過度防禦**（62、57）：只在系統邊界（外部輸入、API 回應、設定載入）驗證。型別已經保證的內部值不要重複檢查。
- **擴充點對 YAGNI**（93、100、61 對 82、20）：已經有第二個實際使用者，或需求明確要求擴充，才引入擴充點。為「以後可能」預留的機制，本身就是異味 20。
- **童軍法則對範圍紀律**（84）：只整理這次實際修改的函式或區塊。整理量大就和功能變更分開提交。
- **拆分迴圈對效能**（55）：預設以可讀性為先；真的在熱路徑上，先量測再決定。
- **尤達寫法**（75）：JS 與 TS 有嚴格比較加 lint，攔截效果已夠，預設不用，除非專案規範要求。
- **語言支援度**（65、66、69）：可選鏈結、空值合併、模式比對視語言與版本而定；沒有原生支援就用等效寫法（如 TypeScript 的判別聯合加窮盡檢查），不要為了套招引入新語法或新依賴。
- **成對的反向招式**（43 與 44、30 與 45、49 與 50）：兩個方向都合理，哪個方向要看改完是否更好讀，不是哪個聽起來更進階。

## 專案規範優先

專案或使用者已經有 lint 規則、formatter 設定、命名慣例、風格規範（例如 CLAUDE.md 或團隊的程式碼風格文件）時，與本 skill 衝突一律以專案規範為準。本 skill 講的是「為什麼這樣整理比較好」，專案規範講的是「這裡約定怎麼寫」；約定優先，因為一致性本身就是可讀性的一部分。
