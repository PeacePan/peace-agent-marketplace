# 程式碼異味（01–25）

目的：找出「需要重構的地方」。

異味只是訊號，不是罪名。先判斷它在這個脈絡下是否真的讓人難讀或難改，再決定要不要處理；要處理時，對應的招式請看 SKILL.md 的「異味速查表」。

每則的「圖卡指令」是原圖卡上給 AI 的標準說法，使用者很可能直接照念，認得它就知道該走哪一招。「訊號與判斷」是補充說明，不是圖卡原文。

---

### 01 過長的函式
- 目的：找出長到難以閱讀的函式
- 訊號與判斷：看的不是行數，而是「能不能一句話說完它做什麼」。需要用註解把函式分段、同一函式混了多個抽象層次，就是訊號。長但線性、單一用途的資料表或設定可以放過。
- 圖卡指令：「找出過長的函式，用『抽取函式』把它們拆開。」

### 02 重複程式碼
- 目的：集中重複邏輯，避免改一處漏一處
- 訊號與判斷：複製貼上後只改幾個字；修一個 bug 要改多處。長得像但「變動原因不同」的程式碼不要硬合併，那是巧合性重複；同一邏輯出現第三次再抽通常比較穩。
- 圖卡指令：「找出重複的程式碼，抽成共用函式。」

### 03 命名不清
- 目的：讓名稱本身就能說明用途
- 訊號與判斷：`x`、`tmp`、`data`、`flag`、`handle`、`doIt`、隨意縮寫，或名稱與實際行為不符。自問：讀的人要看實作才知道它是什麼嗎？
- 圖卡指令：「找出看不出用途的名稱，重新命名。」

### 04 巢狀過深
- 目的：讓多層分支更容易閱讀
- 訊號與判斷：縮排超過三層（if 套 if 再套 for）。優先用提早返回攤平，其次才是抽函式。
- 圖卡指令：「找出巢狀超過三層的地方，把結構攤平。」

### 05 魔術數字
- 目的：讓寫死的數字有明確含義
- 訊號與判斷：程式裡直接出現 `86400`、`0.05`、`3`、`'VIP'` 這類沒有說明的字面值。`0`、`1`、`-1`、空字串這種語意自明的不算；同一個值出現在多處，或代表業務規則（稅率、門檻、逾時），一定要具名。
- 圖卡指令：「把魔術數字改成有名稱的常數。」

### 06 過大的類別
- 目的：找出包辦太多職責的類別
- 訊號與判斷：欄位與方法很多、方法分成幾群且各群用不同的欄位、名稱帶 Manager／Helper／Util 這類包山包海的字眼。
- 圖卡指令：「找出過大的類別，依職責拆開。」

### 07 過長的參數列表
- 目的：降低傳錯引數的機率
- 訊號與判斷：超過 3～4 個參數、呼叫端得對照順序、連續幾個同型別的參數容易傳反。
- 圖卡指令：「找出引數太多的函式，整理參數列表。」

### 08 無用程式碼
- 目的：移除已經用不到的程式碼
- 訊號與判斷：沒有呼叫端的函式、永遠不成立的分支、被註解掉的程式碼、沒用到的 import 與變數。刪之前先全專案搜尋，含動態引用、設定檔、對外 API；版本控制已有歷史，不需要留註解版。
- 圖卡指令：「找出沒有任何呼叫端的程式碼並刪除。」

### 09 散彈式修改
- 目的：避免一個改動散落在多個檔案
- 訊號與判斷：新增一個欄位或規則要同時改好幾個檔案，而且每處只改一點點。
- 圖卡指令：「找出只改一件事、卻得動到好幾個檔案的地方。」

### 10 發散式變更
- 目的：拆開因不同原因而修改的部分
- 訊號與判斷：同一個檔案或類別會因為完全不同的原因被修改（改計價規則動它、改報表格式也動它）。和 09 相反：09 是一個變更散到多處，10 是多種變更擠在一處。
- 圖卡指令：「找出常因不同需求而修改的元件，依職責拆開。」

### 11 義大利麵式程式碼
- 目的：理順交錯的執行流程
- 訊號與判斷：靠旗標跳來跳去、跨函式共享可變狀態、呼叫順序有沒寫出來的隱含要求，很難追蹤誰先誰後。
- 圖卡指令：「整理糾結的流程，讓執行順序可以一路追蹤。」

### 12 全域變數
- 目的：避免變數從各處被任意改寫
- 訊號與判斷：模組層級的可變變數、被各處直接讀寫的單例。常數與不可變設定不算；主要危害是難以測試與順序相依。
- 圖卡指令：「找出全域變數，改成透過引數傳入。」

### 13 特性依戀
- 目的：讓操作靠近它主要使用的資料
- 訊號與判斷：函式裡大部分是在讀取另一個物件的欄位（`a.b.x + a.b.y …`），自己所在的類別反而幾乎沒用到。
- 圖卡指令：「把大量使用其他類別資料的函式移到該類別。」

### 14 資料群聚
- 目的：把總是一起出現的值放在一起
- 訊號與判斷：同樣的 2～3 個欄位或參數總是成組出現（起始日與結束日、x 與 y 與 z），拿掉其中一個就沒有意義。
- 圖卡指令：「將經常一起傳遞的值封裝成一組。」

### 15 過度依賴基本型別
- 目的：用專用型別表達領域概念
- 訊號與判斷：用 string 表示電話、信箱、金額、各種 ID，用 number 表示帶單位的量。只有在容易混淆（兩種 ID 都是 string）或帶驗證規則時才值得包；TypeScript 可用 branded type。
- 圖卡指令：「把電話號碼這類值封裝成專用型別。」

### 16 重複的 switch
- 目的：找出散落各處的相同分支
- 訊號與判斷：多處對同一個「種類或狀態」做 switch 或 if-else 鏈；新增一種種類就得同步改每一處。
- 圖卡指令：「找出多個地方重複出現的 switch 敘述。」

### 17 暫時欄位
- 目的：找出偶爾才會用到的欄位
- 訊號與判斷：欄位只在特定流程才有值，其餘時候是 null 或 undefined，讀的人得猜它何時有效。
- 圖卡指令：「找出只在特定情況下才有值的欄位。」

### 18 呼叫鏈過長
- 目的：縮短一層接一層的呼叫
- 訊號與判斷：`a.b().c().d()`，呼叫端認識整條內部結構，中間任何一環改了就壞。刻意設計的流暢介面（builder、陣列方法鏈、Promise 鏈）不算。
- 圖卡指令：「縮短像 a.b().c().d() 這樣的長呼叫鏈。」

### 19 中間人
- 目的：找出只負責轉呼叫的類別
- 訊號與判斷：一個類別的多數方法只是把呼叫原封不動轉給另一個類別。
- 圖卡指令：「找出把工作原封不動轉交出去的類別。」

### 20 過度泛化
- 目的：清掉為未來預留的擴充機制
- 訊號與判斷：只有一種實作的介面或抽象類、沒用到的參數與 hook、沒人設定的設定項、「以後可能用得到」。
- 圖卡指令：「找出目前用不到、先為擴充而做的機制。」

### 21 閒置類別
- 目的：合併幾乎沒有職責的類別
- 訊號與判斷：職責萎縮到只剩一兩個方法，或只有單一呼叫端。
- 圖卡指令：「找出幾乎沒做事的類別，將它合併。」

### 22 資料類別
- 目的：讓資料與相關行為放在一起
- 訊號與判斷：只有欄位與 getter、setter，所有操作都寫在別的類別。DTO 與 API 回應型別本來就只該有資料，不算；只有「操作它的程式碼散在外面」時才是異味。
- 圖卡指令：「把相關操作移進只存放資料的類別。」

### 23 平行繼承階層
- 目的：找出必須成對擴充的繼承階層
- 訊號與判斷：每為 A 階層新增一個子類別，就得在 B 階層也新增對應的子類別，兩邊的類別名稱常有相同前綴。
- 圖卡指令：「找出一邊新增子類別，另一邊也得跟著加的繼承結構。」

### 24 拒絕繼承
- 目的：找出子類別用不到的繼承功能
- 訊號與判斷：子類別覆寫方法後丟出「不支援」的例外，或幾乎沒用到父類別提供的東西。
- 圖卡指令：「找出幾乎沒用到父類別功能的子類別。」

### 25 類別過度耦合
- 目的：拆開彼此存取內部細節的類別
- 訊號與判斷：兩個類別頻繁存取彼此的內部欄位、互相引用，改其中一個另一個就跟著壞。
- 圖卡指令：「找出互相操作內部資料的類別，降低耦合。」
