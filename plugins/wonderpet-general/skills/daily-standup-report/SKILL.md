# 晨會工作報告（一個指令，Drive 上看當天報告）

晨會每人約一分鐘，要口頭匯報前一個工作日做了什麼。這個 skill 把散在 git、PR、Jira、行事曆、對話紀錄裡的工作整理成一份文件：最上面是一分鐘講得完的口頭稿，下面是保留細節的完整明細，事後想查證時有編號可循。

**同一天只產生一份**：報告檔名以晨會日（下指令當天）命名，先查 Drive 有沒有，有就直接回連結。這樣一天內重複下指令不會堆出一疊重複文件，也不會白跑一輪資料蒐集。

|---|---|
| Drive 資料夾 | 「晨會工作總結」，ID `1wXOevR_09hyv8UFo3ruOnjIwv6SBvxtd` |
| 程式庫 | 本機 `/Users/peacepan/workspace/petpetgo`，GitHub `petpetgo/petpetgo` |
| Jira | RD 專案，cloudId 以 `getAccessibleAtlassianResources` 取得 |

其他人使用時，把這張表換成自己的資料夾、程式庫與 Jira 專案即可。`$ARGUMENTS` 可帶晨會日（`YYYY-MM-DD`，補產過去某天的報告）或「重產」（見步驟 1）。

## 流程

### 步驟 0：決定日期

執行 `scripts/resolve_dates.py`（路徑相對於本 skill 目錄；帶晨會日時加 `--date`）。它依規則回傳工作日範圍與檔名：週二到週五回顧前一天，週一回顧週五到週日。範圍與時區都以它的輸出為準，不要自己心算星期。輸出的 `note` 非空時（例如晨會日是週末）先向使用者確認。

### 步驟 1：當天已有報告就停

用 `mcp__claude_ai_Google_Drive__search_files` 查：

```
parentId = '<資料夾 ID>' and title contains '<title>' and mimeType != 'application/vnd.google-apps.folder'
```

- **有結果**：回覆既有文件的連結與建立時間，一句話說明「今天的報告已經有了」，到此結束，不蒐集資料、不建立任何東西。
- **沒結果**：繼續。
- 使用者明確要求重產（例如補了新資料）：檔名加後綴 `_v2`（再重產則 `_v3`）建立新文件，並在回覆中說明舊文件仍在、需要的話請使用者自行處理，不要替使用者刪除。

### 步驟 2：平行蒐集

五個來源同一輪平行發出，查法與踩雷見 `references/data-sources.md`：git（含所有分支）、GitHub PR 與審查、Jira、Google 行事曆、Claude 對話紀錄（`scripts/sessions_in_range.py`）。

某個來源連不上（最常見是 Jira 憑證）不要卡住：請使用者視情況處理，或跳過該來源，並在報告的「資料來源與限制」交代，受影響的欄位標「未查證」。

### 步驟 3：整合與查證

把五個來源的資料依「功能或問題」歸併，而不是依 commit 或 session：同一項工作可能同時有 commit、PR、Jira 卡與對話紀錄。

查證的原則是：**狀態要有證據，而且證據的時間要對**。對話紀錄是 Claude 自己的回報，不能當證據單獨使用，必須和 PR、commit、Jira 對照（對照表見 `references/data-sources.md` 最後一節）。對不上或無法對照的結論，仍可寫入，但要標明「取自對話紀錄回報、未重跑」。三個容易出錯的點：

- 範圍內才發生的事才列入；晨會當天早上才發生的事（例如今早才合併的 PR）只能當背景，不能寫成昨天的成果。
- PR 被關閉不等於已合併。
- Jira 狀態是現在的狀態，報告中一律叫「目前狀態」。

### 步驟 4：撰寫

照 `references/report-format.md` 的結構與規則寫，HTML 骨架用 `assets/report-template.html`。最容易寫壞的是口頭稿：約 250 字、不報卡號與 PR 號、順序是完成 → 進行中 → 協助他人 → 需要排人的事。編號只放明細表最右欄。

寫完再掃一遍：有沒有客人或員工的個資、有沒有簡體字或英文句子、沒內容的小節是否已刪除、`{{…}}` 是否全部替換。

### 步驟 5：建立 Google 文件

呼叫 `mcp__claude_ai_Google_Drive__create_file`：

- `title`：步驟 0 的檔名（不加副檔名）
- `parentId`：Drive 資料夾 ID
- `contentMimeType`：`text/html`
- `textContent`：步驟 4 的 HTML
- **不要設定** `disableConversionToGoogleType`，Drive 才會把 HTML 轉成原生 Google 文件。

**不要試著上傳 .docx**：Drive 工具只能直接建立 Google 原生文件，上傳 Word 檔得由模型輸出 13～24KB 的 base64 內容，實測會在逐字轉錄時損壞（檔案大小對不上、文字讀回是空白），且 `update_file` 只能改標題與位置、無法覆寫內容。使用者需要 Word 檔時，請他在 Drive 選「檔案 → 下載 → Microsoft Word (.docx)」。

### 步驟 6：驗證與回報

用 `read_file_content` 讀回剛建立的文件，確認：內容不是空的、五個章節標題都在、表格有轉進來、沒有殘留的 `{{`。通過才回報。

回覆使用者時，依序給：

1. 文件連結。
2. 口頭稿全文（使用者常在晨會前直接從對話裡看稿）。
3. 需要使用者留意的事：哪些資料來源沒連上、哪些結論是推算或未重跑、有沒有被略過的 session。

沒檢查到的事要直說，例如表格底色與欄寬只能讀文字、看不到畫面。

## 守則與原因

- **只讀，不寫**：不在 Jira 留言或建票、不改 PR、不推程式碼。這份報告是整理既有事實，副作用越少越安全；真的需要寫入由使用者另行指示。
- **口頭稿不報編號**：使用者明確要求過。聽的人記不住編號，晨會時間也不夠去查，所以口頭稿用白話功能名稱。
- **只寫有證據的狀態**：把「寫完還沒提交」說成「完成」，或把推算說成事實，會讓聽的人做出錯誤判斷，寧可標「未查證」。
- **不放個資**：驗收與診斷資料常含客人、員工的真實資料，報告是團隊共讀的文件，要去識別化。
- **全文繁體中文**：長時間處理英文素材後，旁白與表格狀態字容易混入英文或簡體，寫完要掃描。
