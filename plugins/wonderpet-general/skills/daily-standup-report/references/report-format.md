# 晨會工作報告格式規格

報告給兩種讀者看：晨會上要「口頭講」的人（只需要一分鐘版本），以及事後想「查證細節」的人（需要完整明細）。所以同一份文件分成口頭稿與明細兩層，口頭稿放最前面。

HTML 骨架見 `assets/report-template.html`，照它的結構與行內樣式填內容即可（Google 文件匯入 HTML 時只認行內樣式）。

## 文件結構（順序固定）

1. **標題與抬頭**：`晨會工作總結`；下一行寫工作日期與晨會日期（週一的晨會要列出週五～週日全部日期）、報告人。
2. **一、1 分鐘口頭稿**
3. **二、整體摘要**
4. **三、工作明細**：依性質分小節（開發與交付、小修正合併、協助他人、問題診斷、其他）；沒有內容的小節整段省略。
5. **四、站會可提的待確認事項**
6. **五、資料來源與限制**

## 口頭稿規則

- **篇幅**：約 250 字以內，語速平穩一分鐘講得完。超過就砍，砍的內容在明細裡還在。
- **不報編號**：不提卡號、PR 號。原因：聽的人記不住編號，編號對應的工作還得再去查，晨會時間短沒人會去查，報了等於沒報。改用功能或問題的白話名稱（例如「員工歷史消費與寵物資料查詢」，而不是卡號）。
- **順序**：先講完成的（合併、上線前的小修正），再講進行中的（含狀態：開發完成、驗收通過、等審查），再講協助他人（審查、驗收），最後講需要別人排人或決策的事。
- **狀態要誠實**：只講有證據的狀態。「驗收通過」要有驗收紀錄；「等審查」要有開出的 PR；沒提交的就說「寫完還沒提交」。
- **人名可以留**（例如幫某位同事審查），但不要用代名詞稱呼任何人。
- **留給「時間夠再加」的**：不影響別人的雜務、推算性質的資訊，放在口頭稿下方一行小字，不塞進主稿。

## 明細表格

欄位固定四欄：`工作項目`｜`昨天做了什麼`｜`目前狀態`｜`備查編號`。問題診斷小節第一欄改叫 `事項`、第二欄叫 `結果`。

- **工作項目**：白話名稱，粗體。
- **昨天做了什麼**：條列，保留細節（做了哪些改動、驗證到什麼程度、時間點）。以「為什麼這樣做／結果是什麼」為主，不貼程式碼片段。
- **目前狀態**：用 Jira 的現況文字，顏色對照：完成 `#2E7D32`、IN TESTING `#B26A00`、審核中 `#1F5FA8`、待辦與其他 `#7F7F7F`。表頭下方的說明要寫明「目前狀態為晨會當天早上查詢的 Jira 狀態」，因為它不等於昨天當下的狀態。
- **備查編號**：卡號與 PR 號，一行一個。編號只放這一欄，明細敘述裡不重複寫。

## 待確認事項

只列「別人需要知道或需要動作」的事：沒人接的票、合併前還缺的驗證、沒寫進 Jira 的驗收結果、尚未提交的程式、推算而非實測的結論。每條以工作項目名稱開頭，後面可附卡號。

## 資料來源與限制（必填）

至少交代：

- 涵蓋的日期範圍與時區。
- 用了哪些資料來源；哪個來源當天連不上（例如 Jira 沒連線）就直說，並說明哪些欄位因此未查證。
- 哪些結論是「取自當天對話紀錄的回報、沒有重跑」，哪些是自己另行查證的（PR、Jira）。
- 範圍之後才發生的事不列入（例如晨會當天早上才合併的 PR），避免把「今天」的事說成「昨天」。
- 合併進班車分支不等於已發版到門市。

## 不可放進報告的內容

- 客人姓名、手機、地址、員工編號、會員編號：驗收資料常含這些，一律改成「測試會員」「某位會員」之類的描述。
- 帳密、token、presigned URL。
- 對同事工作品質的評價；只寫事實（例如「補了 2 則測試缺口的 inline comment」）。

## 語言

全文繁體中文。技術名詞、函式名、指令保留原文。寫完掃一遍有沒有混入簡體字或英文句子，常見漏網處是工具呼叫之間的旁白與表格裡的狀態字。
